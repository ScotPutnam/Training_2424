Part 1 — Python (Weeks 1–2)

Data Types & Collections

Python is dynamically typed and interpreted (source → bytecode → Python VM). Core scalar types: int, float, str, bool, None.

nums = [3, 1, 2]
nums.append(4); nums.sort(); nums[0]; nums[-1]; nums[1:3]   # slicing
empty_set = set()          # {} is an empty DICT, not a set!
d = {"a": 1}; d.get("b", 0)   # .get avoids KeyError
"x" in d                   # membership tests keys
Mutability matters: only immutable values (str, int, tuple…) can be dict keys / set members. A tuple of one element needs a comma: (5,).

Truthiness: 0, "", [], {}, set(), None, False are falsy; everything else is truthy. f-strings: f"total: {n * 2}". From collections: deque (O(1) both ends), Counter, defaultdict.

Comprehensions

squares = [x**2 for x in range(10)]              # list
evens   = [x for x in nums if x % 2 == 0]        # with filter
pairs   = {k: v for k, v in zip(keys, vals)}     # dict
uniq    = {x.lower() for x in words}             # set
gen     = (x**2 for x in range(10))              # generator expr — lazy!

Pattern: [expression for item in iterable if condition]. A generator expression (parentheses) produces values on demand instead of building the whole list in memory.

Functions, Lambda & Scope

def greet(name, punct="!"):          # default parameter
    return f"Hello {name}{punct}"

def total(*args, **kwargs):          # args = tuple, kwargs = dict
    return sum(args)

add = lambda a, b: a + b             # single-expression anonymous fn

Scope — LEGB: name lookup goes Local → Enclosing → Global → Built-in. Assigning to a global inside a function needs global x (or nonlocal for the enclosing function's variable).

Gotcha: never use a mutable default (def f(items=[])) — it's created once and shared across calls. Use items=None then items = items or [].

map / filter / reduce / zip

map(str.upper, words)                 # apply fn to each → iterator
filter(lambda x: x > 0, nums)         # keep matching → iterator
from functools import reduce
reduce(lambda a, b: a + b, nums, 0)   # fold to a single value
zip([1,2,3], "abc")                   # pairs: (1,'a'), (2,'b'), (3,'c')

map/filter/zip return lazy iterators — wrap in list() to see results. reduce lives in functools. Comprehensions are usually the more Pythonic equivalent of map/filter.

OOP in Python

class Animal:
    species_count = 0                  # class attribute (shared)

    def __init__(self, name):          # constructor
        self.name = name               # instance attribute
        Animal.species_count += 1

    def speak(self):                   # self = the instance
        return "..."

class Dog(Animal):                     # inheritance
    def __init__(self, name):
        super().__init__(name)
    def speak(self):                   # override
        return "Woof"

    def __str__(self):  return f"Dog({self.name})"   # print() form
    def __eq__(self, o): return self.name == o.name  # == behavior
  • Same 4 pillars as Java. Encapsulation is by convention: _protected, __private (name-mangled) — nothing is enforced.
  • Dunder methods customize built-ins: __init__, __str__, __repr__, __eq__, __len__, __iter__.
  • Everything inherits from object. Multiple inheritance is allowed (MRO resolves order).
  • isinstance(x, Dog) / issubclass(Dog, Animal) for type checks.

Exceptions

try:
    risky()
except ValueError as e:        # specific first
    handle(e)
except (KeyError, IndexError): # multiple types
    ...
except Exception as e:         # broad last
    log(e); raise              # re-raise
else:
    ...                        # runs only if NO exception
finally:
    cleanup()                  # always runs

raise ValueError("bad input")  # throw

class InsufficientFundsError(Exception):   # custom
    pass

All Python exceptions are unchecked — nothing forces handling (unlike Java's checked exceptions). Common built-ins: ValueError, TypeError, KeyError, IndexError, ZeroDivisionError, FileNotFoundError.

Iterators & Generators

An iterable can produce an iterator (__iter__); an iterator yields items one at a time via __next__ and raises StopIteration when done. for loops do this automatically.

def countdown(n):          # generator function — note yield
    while n > 0:
        yield n            # pauses here, resumes on next()
        n -= 1

for x in countdown(3): print(x)   # 3 2 1

Generators are lazy — each value is produced on demand, so they handle huge/infinite sequences in O(1) memory. A function containing yield returns a generator instead of running immediately.

Decorators

A decorator is a function that takes a function and returns a wrapped version — @name above a def is shorthand for f = name(f).

def timer(fn):
    def wrapper(*args, **kwargs):      # accept anything
        start = time.time()
        result = fn(*args, **kwargs)   # call the original
        print(time.time() - start)
        return result
    return wrapper

@timer
def slow_task(): ...                   # slow_task = timer(slow_task)
Flask's @app.get("/items") is exactly this pattern — a decorator registering your function as a route handler.

Logging

Levels (least → most severe): DEBUG → INFO → WARNING → ERROR → CRITICAL. The default root level is WARNING — that's why logging.info() prints nothing until you configure it.

import logging
logging.basicConfig(level=logging.INFO,
                    filename="app.log",
                    format="%(asctime)s %(levelname)s %(message)s")
log = logging.getLogger(__name__)
log.info("started")
log.error("save failed")
Same idea as Logback in Java — only Java's TRACE/DEBUG/INFO/WARN/ERROR maps to Python's DEBUG/INFO/WARNING/ERROR/CRITICAL. Use logging, not print(), in real apps.

The with Statement

with uses a context manager: the file's __enter__ runs at the start and __exit__ runs when the block ends — even if an exception is raised — so the file is always closed. This is what manual open()/close() cannot guarantee.

with open("data.txt", "r") as f:
    for line in f:
        process(line)
# file is closed here, no matter what happened

Pickling

pickle serializes Python objects to a binary format and back. Files must be opened in binary mode.

import pickle

nums = [1, 2, 3]
with open("nums.pkl", "wb") as f:
    pickle.dump(nums, f)          # object → bytes

with open("nums.pkl", "rb") as f:
    restored = pickle.load(f)     # bytes → object
Never unpickle untrusted data — it can execute arbitrary code. For interchange with other systems use JSON.

Flask

Lightweight Python web framework. A route decorator binds a URL to a view function; Flask converts the return value into an HTTP response (dicts become JSON automatically).

from flask import Flask, request, jsonify

app = Flask(__name__)

@app.get("/items")               # or @app.route("/items", methods=["GET"])
def get_items():
    return jsonify(items), 200

@app.post("/items")
def add_item():
    data = request.get_json()    # parse JSON body
    items.append(data)
    return jsonify(data), 201

@app.get("/items/<int:item_id>") # path parameter
def one_item(item_id):
    ...

app.run(debug=True)              # default: http://127.0.0.1:5000
Query params: request.args.get("q"). JSON body: request.get_json(). Return (body, status_code) tuples to control the status.

sqlite3 Module

import sqlite3

conn = sqlite3.connect("app.db")     # creates file if missing
cur  = conn.cursor()

cur.execute("""CREATE TABLE IF NOT EXISTS users (
    id   INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL)""")

cur.execute("INSERT INTO users(name) VALUES (?)", ("Alice",))  # ? = safe param
conn.commit()                        # persist DML!

cur.execute("SELECT id, name FROM users WHERE name = ?", ("Alice",))
row  = cur.fetchone()                # or fetchall()
conn.close()
Two classic exam gotchas: forgetting conn.commit() (inserts vanish) and building SQL with f-strings instead of ? placeholders (SQL injection).

pytest & Coverage

pytest discovers files named test_*.py and functions named test_*, and uses plain assert.

# shipping.py
def shipping_cost(weight):
    if weight <= 0: raise ValueError("invalid")
    return 5 if weight < 10 else 12

# test_shipping.py
import pytest
from shipping import shipping_cost

def test_light_package():
    assert shipping_cost(5) == 5

def test_invalid_weight():
    with pytest.raises(ValueError):
        shipping_cost(0)
pytest                        # run tests
coverage run -m pytest        # run under coverage
coverage report               # % of statements executed
Statement coverage = % of code lines executed by tests. 100% coverage still doesn't prove correctness — it only shows what was exercised.

Part 2 — Java (Weeks 2–3)

Java Basics

Java is a class-based, object-oriented, statically-typed, platform-independent language. Source code (.java) is compiled to bytecode (.class) and executed by the JVM, giving the "write once, run anywhere" property.

  • JDK: Java Development Kit — compiler + tools + JRE.
  • JRE: Runtime Environment — JVM + core libraries.
  • JVM: Java Virtual Machine — runs bytecode.

Compilation Process & the main() Method

Java is a compiled + interpreted hybrid: javac compiles .java source into bytecode (.class files); the java launcher loads them into the JVM, which interprets and JIT-compiles the bytecode for the host platform.

javac Hello.java     # produces Hello.class (bytecode)
java Hello           # JVM executes it

The entry point

public static void main(String[] args) { ... }
  • public — JVM must be able to call it from outside.
  • static — called without creating an object first.
  • void — returns nothing.
  • String[] args — command-line arguments.
Change any of those and the JVM reports "main method not found" — the signature is exact.

Maven

Build-automation and dependency-management tool. Configured by pom.xml (Project Object Model). Dependencies are identified by coordinates: groupId : artifactId : version, downloaded from Maven Central and cached in the local repo (~/.m2).

Standard directory layout

src/main/java        production code
src/main/resources   config (logback.xml, etc.)
src/test/java        test code
target/              build output

Build lifecycle (default) — in order

validate → compile → test → package → verify → install → deploy

Running a phase runs every phase before it: mvn package also validates, compiles, and tests. mvn clean deletes target/ (separate lifecycle).

Strings & the String Pool

String is an immutable reference type. String literals are interned in the string pool (inside the heap) — identical literals share one object. new String("hi") forces a separate heap object.

String a = "hi";
String b = "hi";
String c = new String("hi");
a == b        // true  — same pooled object
a == c        // false — different objects
a.equals(c)   // true  — same characters
Always compare strings with .equals() (or equalsIgnoreCase), never ==.

Because String is immutable, methods like toUpperCase() return a new string. For heavy concatenation in loops, use StringBuilder (append(), then toString()).

Methods to know

length(), charAt(i), substring(a, b), indexOf(s), contains(s), split(regex), trim()/strip(), replace(a, b), toUpperCase(), toLowerCase()

Scanner — Reading Console Input

Scanner sc = new Scanner(System.in);
String line = sc.nextLine();   // whole line
int n       = sc.nextInt();    // next int token
double d    = sc.nextDouble();
Gotcha: nextInt() leaves the newline in the buffer — a following nextLine() returns "". Fix: call an extra sc.nextLine() after numeric reads.

    int mid = lo + (hi - lo) / 2;

Common Big-O classes (fastest → slowest)

O(1) constant → O(log n) logarithmic → O(n) linear → O(n log n) good sorts → O(n²) nested loops → O(2ⁿ) exponential.

Big-O describes the worst-case growth rate as input size grows; constants and lower-order terms are dropped.

SOLID Principles

  • S — Single Responsibility: a class has one reason to change.
  • O — Open/Closed: open for extension, closed for modification.
  • L — Liskov Substitution: a subclass must be usable anywhere its parent is expected.
  • I — Interface Segregation: many small interfaces beat one fat one.
  • D — Dependency Inversion: depend on abstractions, not concrete classes.

Debugging & Stack Traces

A stack trace prints the call chain at the moment an exception was thrown — read it top-down: the first line is the exception + message, the first your-package frame below it is usually where to look. Caused by: sections show the root cause.

Debugger workflow: set a breakpoint → run in debug mode → step over (next line), step into (enter the call), step out (finish current method) → inspect variables / watch expressions.

Arrays

Fixed-length, zero-indexed, reference-type container holding either primitives or objects. Length is set at creation and can never change.

int[] nums = new int[5];        // all zeros
int[] a = {1, 2, 3};            // literal
String[][] grid = new String[3][4]; // 2D

nums.length;                    // field, not method
Arrays.toString(a);             // "[1, 2, 3]"
Arrays.equals(a, b);            // content comparison (== compares references)
Gotcha: ArrayIndexOutOfBoundsException if you touch arr[arr.length]. Prefer < in loop bounds, not <=.

Control Flow & Loops

  • if / else if / else — branch on boolean expressions.
  • switch — since Java 14 supports arrow syntax: case 1 -> ...;
  • for, while, do-while, and enhanced for (T x : coll).
  • break / continue (with optional labels).

Boolean expressions & short-circuiting

&& and || short-circuit; & and | always evaluate both sides. Only boolean is allowed in an if condition — no truthy/falsy coercion.

Classes vs Objects

A class is a blueprint. An object is a concrete instance created with new. Class members: fields (state), methods (behavior), constructors (initialization), and inner types.

public class Dog {
    private String name;             // field
    public Dog(String name) {        // constructor
        this.name = name;
    }
    public String bark() {           // method
        return name + ": Woof!";
    }
}
Dog d = new Dog("Rex");              // object

Non-access modifiers

  • static — belongs to the class, not instances.
  • final — variable = constant; method = cannot override; class = cannot extend.
  • abstract — class cannot be instantiated; method has no body.
  • synchronized — one thread at a time on the object monitor.
  • volatile — reads/writes go straight to main memory.
  • transient — skipped by default serialization.

Static Members

Static fields/methods belong to the class rather than instances. They live in the method area (metaspace) and exist from class-load to shutdown. Called via ClassName.member and cannot use this.

Rule: A static method cannot directly access instance members; an instance method can access static members.

JVM Memory: Stack, Heap, GC

  • Stack — per-thread frames for method calls; local primitives & object references live here. LIFO. StackOverflowError when frames exceed size.
  • Heap — where all new objects live, shared across threads. Managed by the Garbage Collector.
  • Metaspace — class metadata & static fields (replaced PermGen in Java 8).

Garbage Collection

GC reclaims objects that are no longer reachable from any live thread root (stacks, statics, JNI). You cannot force GC; System.gc() is only a hint. Generations: young (Eden + Survivors), old, GC algorithms: Serial, Parallel, G1 (default), ZGC.

finalize() is deprecated — use try-with-resources and the AutoCloseable interface.

The 4 OOP Pillars

  1. Encapsulation — bundle data + behavior, hide state behind accessors. Achieved with private fields + public getters/setters.
  2. Abstraction — expose what, hide how. Achieved with interfaces and abstract classes.
  3. Inheritance — an "is-a" relationship. extends for classes, implements for interfaces.
  4. Polymorphism — one interface, many implementations. Compile-time (overloading) or runtime (overriding / dynamic dispatch).

Inheritance

A subclass inherits all non-private, non-static members of its superclass. Java has single class inheritance but a class may implement multiple interfaces. super() calls the parent constructor (implicit if omitted).

class Animal { void speak() { System.out.println("..."); } }
class Dog extends Animal {
    @Override void speak() { System.out.println("Woof"); }
}

Polymorphism

Two forms:

  • Compile-time (static) — method overloading. Compiler picks the method from the argument list.
  • Runtime (dynamic) — method overriding. JVM dispatches to the concrete class of the object.
Animal a = new Dog();
a.speak();   // "Woof" — runtime dispatch on the actual object

Casting Objects

  • Upcast — child → parent, implicit and always safe. Animal a = new Dog();
  • Downcast — parent → child, explicit and requires a runtime check. Fails with ClassCastException if the object is not actually that type.
if (a instanceof Dog d) {   // pattern matching (Java 16+)
    d.fetch();
}

Object Class, equals() & hashCode()

java.lang.Object is the implicit parent of every class. Key methods to know:

  • equals(Object o) — logical equality. Default is ==.
  • hashCode() — bucket for hash collections.
  • toString() — string form.
  • getClass(), clone(), wait(), notify().
Contract: If a.equals(b) is true, then a.hashCode() == b.hashCode(). Violating this breaks HashMap, HashSet, etc.

Method Recursion

A method that calls itself. Every recursive method needs a base case to stop, and a recursive step that moves toward the base case. Deep recursion blows the stack — StackOverflowError. Java does not do tail-call optimization; prefer iteration for very deep problems.

Exceptions

Throwable is the root. Two branches:

  • Error — serious JVM problems (OutOfMemoryError, StackOverflowError). Don't catch.
  • Exception — application-level.
    • Checked — must be declared or handled (IOException, SQLException).
    • Unchecked (RuntimeException) — NullPointerException, IllegalArgumentException, ClassCastException.

Handling

try {
    risky();
} catch (SpecificException e) {
    log(e);
} catch (Exception e) {
    throw new RuntimeException(e);
} finally {
    cleanup();   // runs whether or not an exception was thrown
}

// try-with-resources — auto-closes anything implementing AutoCloseable
try (BufferedReader r = new BufferedReader(new FileReader("f"))) {
    ...
}

Custom exceptions

public class InsufficientFundsException extends Exception {
    public InsufficientFundsException(String msg) { super(msg); }
}
Extend Exception for checked, RuntimeException for unchecked.

Wrapper Classes

Every primitive has an object wrapper: Integer, Long, Double, Boolean, Character, etc. Needed because generics only accept reference types (List<int> is illegal — use List<Integer>).

Autoboxing converts primitive → wrapper; unboxing the reverse. Beware NullPointerException unboxing a null Integer, and cache-based equality: Integer.valueOf(127) == Integer.valueOf(127) is true, but Integer.valueOf(128) == Integer.valueOf(128) is false.

Collections Framework

Root interface: java.util.Collection. Hierarchy:

  • Collection
    • List — ordered, allows duplicates.
    • Set — no duplicates.
    • Queue — FIFO (or priority) processing.
  • Map — key → value, separate hierarchy (does not extend Collection).

Queue Interface & PriorityQueue

Queue = FIFO by default. Methods: offer/poll/peek (null on failure) or add/remove/element (throw on failure).

PriorityQueue is a min-heap; the head is always the least element per natural ordering or supplied Comparator. Not FIFO, not sorted iteration — just guaranteed next minimum on poll().

Deque = double-ended queue, use ArrayDeque.

Lambdas & Functional Interfaces

A functional interface has exactly one abstract method (@FunctionalInterface). A lambda is shorthand for implementing it.

Runnable r = () -> System.out.println("hi");

Function<Integer, Integer> square = n -> n * n;

File I/O

Legacy: java.io (File, FileReader, BufferedReader). Modern: java.nio.file (Path, Paths, Files).

// Read all lines (small files)
List<String> lines = Files.readAllLines(Paths.get("data.txt"));

// Stream lines (large files)

// Write

// Buffered reader
try (BufferedReader br = Files.newBufferedReader(Paths.get("data.txt"))) {
    String line;
    while ((line = br.readLine()) != null) { ... }
}

Logback Logging

Logback is a popular SLF4J-compatible logging backend. Levels (least → most severe): TRACE, DEBUG, INFO, WARN, ERROR. Configured via logback.xml on the classpath.

private static final Logger log = LoggerFactory.getLogger(MyClass.class);
log.info("User {} logged in", userId);
log.error("Failed to save", ex);
Use parameterized messages ({}) — SLF4J skips string concatenation if the level is disabled.

Part 3 — SQL & JDBC (Week 4)

SQL Overview

SQL (Structured Query Language) is a declarative language for managing relational data. You describe the result you want; the query planner decides how to fetch it. Data lives in tables (relations) made of rows (tuples) and columns (attributes), with keys tying rows together.

Database Vendors

  • MySQL / MariaDB — LAMP staple, dual-licensed. Fast, ubiquitous.
  • PostgreSQL — standards-compliant, rich types (JSONB, arrays, ranges), extensible.
  • Oracle — enterprise, per-core licensing, PL/SQL.
  • SQL Server — Microsoft stack, T-SQL, tight .NET/Azure integration.
  • SQLite — embedded, single file, zero-config; great for tests and desktop apps.

Constraints

  • NOT NULL — value required.
  • UNIQUE — no duplicates (NULL allowed once).
  • PRIMARY KEY — NOT NULL + UNIQUE + one per table (identity).
  • FOREIGN KEY — references a row in another table.
  • CHECK — arbitrary boolean condition.
  • DEFAULT — value used when INSERT omits column.

Normalization

Progressive process of decomposing tables to eliminate redundancy & anomalies.

  • 1NF — atomic values, no repeating groups; each row unique.
  • 2NF — 1NF + every non-key column depends on the whole primary key (no partial dependencies).
  • 3NF — 2NF + no transitive dependencies (non-key columns don't depend on other non-key columns).
  • BCNF — stricter 3NF; every determinant is a candidate key.
Rule of thumb: normalize for OLTP, denormalize selectively for OLAP/reporting.

Referential Integrity

Foreign keys guarantee referenced rows exist. Cascade behavior on the parent:

  • ON DELETE CASCADE — children deleted with parent.
  • ON DELETE SET NULL — child FK becomes NULL.
  • ON DELETE RESTRICT / NO ACTION — blocks deletion.

Table Relationships / Multiplicity

  • One-to-one — rarely needed; usually combine into one table.
  • One-to-many — FK on the many side (Department → Employees).
  • Many-to-many — junction/bridge table with two FKs (Students ↔ Courses via Enrollments).

ACID Properties

  • Atomicity — all statements in a transaction succeed together or none do.
  • Consistency — transaction moves DB from one valid state to another (constraints upheld).
  • Isolation — concurrent transactions don't interfere. Levels: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE.
  • Durability — committed changes survive crashes (write-ahead log).

Joins

  • INNER JOIN — rows matching in both tables.
  • LEFT (OUTER) JOIN — all left rows + matched right rows (NULL if no match).
  • RIGHT (OUTER) JOIN — mirror of LEFT.
  • FULL (OUTER) JOIN — union of LEFT and RIGHT.
  • CROSS JOIN — Cartesian product (every left × every right). No ON clause.
  • SELF JOIN — table joined to itself using aliases.
SELECT e.name, d.name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id;

Set Operations

Combine result sets of two SELECTs with the same columns / compatible types.

  • UNION — combined, duplicates removed.
  • UNION ALL — combined, duplicates kept (faster).
  • INTERSECT — rows in both.
  • EXCEPT / MINUS — rows in first not in second.

Indexes

Auxiliary structure (usually a B-tree) that speeds up lookups on indexed columns at the cost of extra storage and slower writes.

  • B-tree — default; range and equality queries.
  • Hash — equality only, no range.
  • Unique — enforces UNIQUE constraint.
  • Composite — multi-column, order matters (leftmost prefix rule).
  • Partial — only indexes rows meeting a predicate.
  • Clustered vs Non-clustered — clustered stores rows in index order; non-clustered points to rows.
CREATE INDEX idx_emp_dept ON employees(dept_id);
CREATE UNIQUE INDEX idx_emp_email ON employees(email);
Every INSERT/UPDATE/DELETE has to update every index. Don't over-index write-heavy tables.

Views

A view is a stored SELECT, treated as a virtual table. Regular views re-run their query each time; materialized views cache results and must be refreshed.

CREATE VIEW active_employees AS
SELECT id, name FROM employees WHERE status = 'ACTIVE';

CREATE OR REPLACE VIEW ...;   -- update definition
DROP VIEW active_employees;

Advantages: abstraction, security (grant on view instead of raw tables), simplified reusable queries, backward compatibility during schema changes.

Stored Procedures

Server-side compiled routines. Can take parameters, return result sets, encapsulate business logic, run inside a transaction.

CREATE PROCEDURE raise_salary(emp_id INT, pct NUMERIC)
LANGUAGE plpgsql AS $$
BEGIN
  UPDATE employees SET salary = salary * (1 + pct/100) WHERE id = emp_id;
END; $$;

CALL raise_salary(42, 5);

Difference vs function: functions must return a value and are used inside SQL expressions; procedures are called via CALL, can do TCL.

Part 4 — QEA / Testing (Week 5)

SDLC & Waterfall

SDLC phases: Planning → Requirements/Analysis → Design → Implementation → Testing → Deployment → Maintenance.

Waterfall executes the phases strictly in sequence — each phase must finish before the next begins. Testing happens late, change is expensive, but scope/docs are fixed up front. Suits stable, well-understood, regulated projects.

Cost of a bug grows by phase: requirements ≈ $1, development ≈ $10, testing ≈ $100, production ≈ $1000+. That's the argument for testing early ("shift-left").

Agile Manifesto values: individuals & interactions over processes & tools · working software over comprehensive documentation · customer collaboration over contract negotiation · responding to change over following a plan.

Scrum roles

  • Scrum Master — facilitates, removes impediments, coaches the process.
  • Developers — everyone building the increment (includes testers).

The 7 Testing Principles (ISTQB)

  1. Testing shows the presence of defects, not their absence.
  2. Exhaustive testing is impossible — use risk & techniques to prioritize.
  3. Early testing saves time and money (shift-left).
  4. Defects cluster — a few modules contain most bugs (Pareto).
  5. Pesticide paradox — repeating the same tests stops finding new bugs; refresh them.
  6. Testing is context-dependent — a banking app and a game need different testing.
  7. Absence-of-errors fallacy — a bug-free product that doesn't meet user needs still fails.

Error vs Defect vs Failure

Error (mistake) — a human action producing a wrong result (developer writes >= instead of >).
Defect (bug/fault) — the flaw in the code/artifact caused by the error.
Failure — the observable wrong behavior when the defect executes at runtime.

Chain: error → defect → failure. A defect can hide forever without causing a failure if that code never runs with triggering input.

Coverage measures: statement coverage = % of statements executed; branch/decision coverage = % of decision outcomes (true & false) exercised. Branch coverage is stronger — 100% branch implies 100% statement, not vice versa. Grey-box = partial knowledge.

Test Design Techniques

Equivalence Partitioning (EP)

Split inputs into classes expected to behave the same; test one value per class. Age field accepting 18–65 → partitions: <18 (invalid), 18–65 (valid), >65 (invalid).

Boundary Value Analysis (BVA)

Bugs live at the edges. For 18–65 test 17, 18 and 65, 66 (two-value) or 17, 18, 19 / 64, 65, 66 (three-value).

Decision Table Testing

For business rules with combinations of conditions: one column per rule, conditions (T/F) on top, actions below — every combination gets a test. n binary conditions → up to 2ⁿ rules.

State Transition Testing

For systems whose behavior depends on history (cart, login lockout, order status): model states, events, transitions; test valid transitions and attempt invalid ones.

Use Case Testing

Derive tests from user-system interaction flows: main path + alternate + exception paths.

Experience-based

Error guessing (attack likely weak spots: nulls, empty, 0, negatives, huge input) · exploratory testing (simultaneous learning, design, execution — session-based) · checklist testing.

Positive testing confirms valid input works; negative testing confirms invalid input is handled gracefully.

Test Cases, Test Plans & RTM

Test case fields: ID, title, preconditions, test data, steps, expected result, actual result, status (pass/fail), priority. Written so anyone can execute it and get the same verdict.

Test plan — scope, approach, resources, schedule, entry/exit criteria, risks. Test suite — an organized group of test cases.

RTM (Requirements Traceability Matrix) — maps every requirement → the test cases covering it, proving coverage and showing the blast radius when a requirement changes. Columns typically: Req ID → Story → Test Case IDs → Status.

Data-driven testing — one parameterized script run against a table of input/expected-output rows (like the coupon CSV exercise).

Defect Lifecycle

Minimal flow: New → Assigned → Fixed → Retest → Closed, with Reopened looping back to the developer if retest fails.

Other resolutions: Duplicate (link to the original), Cannot reproduce (needs more info), Won't fix / Deferred (business decision — document the risk), Not a defect (works as specified).

A good defect report carries: steps to reproduce, expected vs actual, environment, build/version, logs, screenshots.

Part 5 — Unit Testing (Week 6)

Unit Tests & the FIRST Principles

A unit test verifies the behavior of a small, isolated piece of code — typically a single method or function — without external dependencies. Unit tests are fast (milliseconds), form the base of the testing pyramid, and pinpoint defects with more precision than higher-level tests.

FIRST — qualities of a good unit test:

  • F — Fast: milliseconds; slow tests don't get run.
  • I — Isolated/Independent: no dependence on other tests or shared state.
  • R — Repeatable: same result every time, in any environment (no LocalDate.now(), no live network calls — use fixed data and mocks).
  • S — Self-validating: pass/fail via assertions, no manual inspection.
  • T — Timely: written close in time to the code (ideally first — TDD).
Typical defects unit tests catch: flow-control failures, improper logic, wrong variables used, malformed environment variables, misconfigured properties.
Interview scenario: a test that passes locally but fails in CI because it checks today's date violates Repeatable — fix it with a fixed date (LocalDate.of(2024,1,6)) or an injectable clock.

TDD vs BDD

Test-Driven Development: write the tests first, then code to pass them. Cycle: Red → Green → Refactor (write a failing test → write the minimum code to pass → clean up). Benefits: clear goals for developers, requirements covered by tests from day one, testers and developers stay on the same page.

Behavior-Driven Development: extends TDD by describing behavior in business-readable language — Given / When / Then (Gherkin syntax, run by tools like Cucumber). Non-technical stakeholders can read and help write the specifications.

FocusCode units behave correctlySystem behavior meets business expectations

JUnit is Java's standard testing framework. A method annotated @Test is a test case; by default it passes if no unhandled exception is thrown — assertions are what make it meaningful.

Assertions, assertThrows & assertAll

assertTrue(cond);  assertFalse(cond);

Testing exceptions

    IndexOutOfBoundsException.class,

Grouped assertions — assertAll

    () -> assertEquals("John", user.getFirstName()),

assertAll runs every assertion and reports all failures instead of stopping at the first — this is JUnit's soft assertion.

Hard vs soft asserts (interview favorite): a hard assert stops the test at the first failure (plain assertEquals); a soft assert collects all failures and reports them together at the end (assertAll).

Parameterized Tests, Skipping & Suites

Run one test method against many data sets — the heart of data-driven testing (test data can even come from a CSV).

// JUnit 5
@ParameterizedTest
@ValueSource(ints = {2, 4, 6})
void isEven_true(int n) { assertTrue(calc.isEven(n)); }

@ParameterizedTest
@CsvSource({"10,true", "9,false"})          // or @CsvFileSource(resources="/data.csv")
void isEven(int n, boolean expected) {
    assertEquals(expected, calc.isEven(n));
}
// JUnit 4 style
@RunWith(Parameterized.class)
public class EvenTest {
    @Parameters public static Collection<Object[]> inputs() {
        return Arrays.asList(new Object[][]{ {10, true}, {9, false} });
    }
    @Parameter      public int number;      // index 0
    @Parameter(1)   public boolean isEven;  // index 1
    @Test public void check() { assertEquals(isEven, number % 2 == 0); }
}

Skipping: @Disabled("reason") (JUnit 5) / @Ignore (JUnit 4) on a method or the whole class — for broken, obsolete, or in-refactor tests.

Suites: group related test classes so they run together (JUnit 4: @RunWith(Suite.class) + @Suite.SuiteClasses({A.class, B.class})) — keeps build/test scripts lean.

Mockito — Mocks, Stubs & Spies

When the class under test has dependencies (service → repository → DB), Mockito replaces them with fakes so the unit stays isolated.

  • Mock — a complete fake: every method returns defaults (null / 0 / false / empty) until stubbed. Full isolation.
  • Stub — a predefined answer for a specific call: the when/then pattern.
  • Spy — a real object with selective stubbing: unstubbed methods run the real implementation.
List<String> mockList = mock(List.class);
mockList.add("item");                  // does nothing, returns default

List<String> spyList = spy(new ArrayList<>());
spyList.add("item");                   // REALLY adds — real behavior

Stubbing — when / then

when(repo.findById(1L)).thenReturn(new User("John"));
when(repo.findById(-1L)).thenThrow(new IllegalArgumentException());
doNothing().when(mock).voidMethod();   // for void methods
Arguments are tracked: when(greeter.greet("Ted")).thenReturn("Hello Ted") only fires for "Ted" — any other argument returns the default value. Matchers like anyInt(), anyString(), eq(x) loosen this.

Annotations

@ExtendWith(MockitoExtension.class)    // JUnit 5 (or MockitoAnnotations.openMocks(this))
class PaymentServiceTest {
    @Mock        PaymentGateway gateway;   // fake dependency
    @InjectMocks PaymentService service;   // real object, mock injected

    @Test void processPayment_validCard_succeeds() {
        when(gateway.charge(anyDouble())).thenReturn(new PaymentResult(true, "TXN1"));
        assertTrue(service.processPayment(99.99).isSuccess());
        verify(gateway).charge(99.99);
    }
}
@InjectMocks tries constructor → setter → field injection, in that order. Test structure: Arrange (stub) → Act (call) → Assert (result) → Verify (interactions).

Verifying Method Calls

Assertions check the result; verify() checks the path — that the code under test actually interacted with its dependencies correctly (e.g., input really was validated, save really was called).

verify(mock).method(args);                    // exactly once (default)
verify(mock, times(2)).addContent(5, 5);      // exactly twice
verify(mock, never()).delete(any());          // never called
verify(mock, atLeast(1)).addContent(5, 5);
verify(mock, atMost(2)).addContent(5, 5);

Python unittest (built-in)

Java-style xUnit framework in the standard library: tests are methods on a class extending unittest.TestCase, assertions are methods on self.

import unittest

class CartTest(unittest.TestCase):
    @classmethod
    def setUpClass(cls): ...          # once, like @BeforeAll

    def setUp(self):                  # before EACH test, like @BeforeEach
        self.cart = Cart()

    def test_add(self):
        self.cart.add("apple")
        self.assertEqual(self.cart.count(), 1)
        self.assertTrue(self.cart.has("apple"))
        with self.assertRaises(ValueError):
            self.cart.add(None)

    def tearDown(self): ...           # after each test

if __name__ == "__main__":
    unittest.main()

Mock & MagicMock (unittest.mock)

A Mock accepts any attribute/method call and records how it was used. MagicMock = Mock + pre-configured magic (dunder) methods.

from unittest.mock import Mock, MagicMock

# len(Mock()) → TypeError! Plain Mock has no magic methods

side_effect — beyond simple returns

m.fetch.side_effect = TimeoutError("down")        # raise an exception
m.fetch.side_effect = [1, 2, 3]                   # successive calls → 1, then 2, then 3
m.fetch.side_effect = lambda x: x * 2             # computed from arguments
Rule of thumb: use MagicMock by default; side_effect beats return_value when you need exceptions, sequences, or input-dependent answers.

Patching & pytest-mock

patch temporarily replaces a real object with a mock for the duration of a test, then restores it.

from unittest.mock import patch

@patch("mymodule.api_client")            # decorator — mock passed as argument
def test_call(mock_client):
    mock_client.call.return_value = {"ok": True}
    assert my_function() == {"ok": True}

with patch("mymodule.api_client") as mock_client:   # context manager
    ...
Golden rule: patch where it's USED, not where it's defined. from external_lib import api_client creates a local reference in mymodule — patching external_lib.api_client changes the original, but mymodule keeps its own reference. Patch mymodule.api_client.

Multiple @patch decorators inject bottom-up (closest decorator = first parameter). pytest-mock wraps all this in a mocker fixture with automatic cleanup:

def test_call(mocker):                    # pytest-mock plugin
    mock_client = mocker.patch("mymodule.api_client")
    mock_client.call.return_value = {"ok": True}
    assert my_function() == {"ok": True}

Acceptance Testing Types

Acceptance testing validates the application meets the owner's and end users' requirements — the confidence gate before release.

  • UAT — end users confirm the system meets their needs; hard to automate (subjective).
  • Usability testing — is it natural and intuitive? Multiple users struggling in the same place = design defect.
  • Alpha testing — first round, by internal personnel (not testers), before wider release.
  • Beta testing — limited release to external end users for real-world feedback.
  • Contractual / Regulatory — verify legal & contract compliance, often witnessed by an authority (e.g., SEC auditor).
  • Operational (OAT) — admin concerns: backups, log generation, install/uninstall, security vulnerabilities.
Smoke testingSanity testing
WhatBasic/critical functionality of the whole build ("does it even turn on?")Focused check that a specific new feature/fix behaves — a subset of regression
WhenFirst thing on a new buildAfter a change, before deeper regression

Non-Functional Testing

System-level testing of how well the app works rather than what it does. Tied to SLAs — promised performance levels.

TypeQuestion it answers
PerformanceDoes it meet responsiveness & throughput expectations?
LoadHow does it behave under varying traffic levels (auto-scaling)?
StressKeep increasing load — where is the breaking point?
Endurance (soak)Can it sustain normal load over a long time? (finds memory leaks, log bloat)
CompatibilityConsistent across browsers, OSes, devices?
PenetrationDoes security hold against known attacks?
Distinguish the trio: load = varying levels, stress = beyond limits to find the break, endurance = normal load for a long duration.

Test Team Roles & Documents

Roles

  • Test Manager — owns the test process: strategy, team, resources, coordination.
  • Tester — writes/executes test cases, reports bugs, verifies fixes.
  • Business Analyst — bridge between business and technical teams; clears up requirement misunderstandings.
  • Stakeholders — provide requirements and feedback, review results, decide.
Tester independence: testers assume "this app has defects and I'll find them" (pessimistic); developers assume "it works, build on it" (optimistic). Independent testers make defect detection unbiased — but quality is everyone's responsibility.

Documents

  • Test Plan — master document: strategy, objectives, schedule, estimates, deliverables.
  • Test Strategy — the approaches/techniques (part of the plan), with effort & cost estimates.
  • Test Schedule — timeline of testing activities; a living document in Agile.
  • SRS — Software Requirements Specification: functional + non-functional requirements; basis for validation.
  • RTM — maps requirements/user stories → test cases (→ defects); proves coverage.
  • Test Progress Report — ongoing status: executed / passed / failed / defects.
  • Test Summary Report — aggregated results per test run/cycle, compared against exit criteria.
  • Defect Report — severity, priority, environment, steps to reproduce.

Software Testing Life Cycle (STLC)

  1. Requirement Analysis — study requirements (functional & non-functional); draft the RTM.
  2. Test Planning — test manager drafts the plan, effort/cost estimates, resources & environment needs.
  3. Test Case Development — write test cases, scripts, and test data (parallel with environment setup).
  4. Environment Setup — replicate production conditions; smoke-test the environment.
  5. Test Execution — run scripts, log defects, retest, report; track defects to closure.
  6. Test Cycle Closure — analyze results and artifacts; capture lessons learned; client sign-off.
Each phase has entry/exit criteria — e.g., execution can't start until the environment is ready and planned test cases exist; closure requires all tests executed and defects tracked to closure.
